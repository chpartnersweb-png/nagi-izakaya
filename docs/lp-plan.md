## 1. コンセプトと来店導線

**「米と魚、今夜は凪で。」**

料理の色、器の表情、木の温もりを主役にした、親しみのある現代的な和のLP。高級店のように緊張させず、賑やかな販促物にも寄せない。白い紙の余白と食卓の濃い色を切り替え、写真の大きさ・位置・間隔でページにリズムをつくる。

来訪者の流れは「おいしそう → 食べたい料理と価格が分かる → 日本酒・店内を知る → 場所と営業時間を確認 → 電話で予約・問い合わせ」。主要CTAは電話、副導線は地図、補助導線はInstagramとする。未提供のネット予約サービスや予約フォームは追加しない。

## 3. デザイン仕様

- 背景：生成り `#F5F1E8`。写真以外の部分を落ち着かせる。
- 文字：墨茶 `#28231E`。本文のコントラストを確保する。
- 濃色面：深い藍 `#243B42`。日本酒セクションに限定して使用。
- アクセント：控えめな朱 `#A24632`。予約ボタン、見出しの小印、価格の補助に使用。
- 見出しは日本語明朝体、営業時間・住所・本文は可読性の高いゴシック体。フォントは使用ウェイトを絞る。
- PC本文の幅はおおむね1120〜1200px。大写真だけをその枠から外し、左右に余白の差をつける。
- 写真は原則長方形。丸み、影、囲み枠は最小限。全セクションを同じカードや左右交互の2列構成にしない。
- 縦書きは短い装飾見出しに限る。料金、説明、営業時間は横書き。
- モバイル本文は原則16px以上、操作面は44px以上を目安とし、価格は画像に焼き込まずHTMLで表示する。

## 4. ページ構成とレイアウト

### A. ヘッダーとヒーロー

背景画像を画面いっぱいに敷く。PC／スマートフォンとも初期画面は原則100svhとし、固定UIを含む収まりを検証する。左テキスト・右画像への分割は行わない。

中央には生成した「大きな凪／下に小さな居酒屋」のロゴと、短いコピー「米と魚、今夜は凪で。」のみ。縦積みしたロゴとコピーを一つのグループとして中央に配置する。下端に「日暮里駅直結・徒歩1分」と小さなスクロール案内を置く。メニューの羅列や特徴3項目、長文説明をヒーローへ詰め込まない。

ヘッダーは細い帯。メニュー、店内、アクセス、電話CTAを配置する。ヒーロー上では白系ロゴ、スクロール後は生成りの背景と墨色ロゴへ切り替える。スマートフォンは小さなロゴとメニューボタンに整理する。

生成ヒーローは、木の食卓、土鍋から立つ湯気、日本酒の器、柔らかい灯りで食事の期待感をつくる。特定の提供料理や実店舗の内装を再現したものとして扱わない。画像付近に「イメージビジュアル」と控えめに明記し、商品写真・店舗写真と区別する。

試作済み素材：`src/assets/generated/nagi-hero-concept-v1.png`、`src/assets/generated/nagi-logo-sumi-v1.png`。生成後に画像内容と文字を目視確認済み。使用プロンプトは `generated-image-brief.md` に保存した。中央ロゴの大きさ・背景とのコントラスト・モバイルでの切り抜きは、ページ実装時に調整する。

### B. 導入「米と魚に、こだわる。」

生成りの余白に短い文章を置き、その下から実写の料理集合写真 `S__49111058_0.jpg` を大きく見せる。写真を挟んで「魚」「米」「酒」の小さな見出しを添え、特徴を各1文で伝える。アイコン付きの3カードにはしない。

コピー案：「朝一番に入荷した魚と、こだわりの米。日本酒は20種以上から。日暮里の食卓で、気軽な一杯も、みんなの集まりも。」

### C. メニュー「今夜の、食べたい。」

**5品の料理写真・名称・価格を同じ表示領域に置くことを最優先とする。写真対応の確定が前提。**

前半は鍋3品のまとまり。通風鍋を幅広の大写真で見せ、余白に名称・価格・短い説明を添える。その下に西京もつ鍋とエビ麻辣鍋の2品を、異なる高さから始まる写真で配置する。価格・文字サイズ・情報量は揃える。

後半は、刺身と土鍋ご飯の対。刺身は器全体が見える横写真、土鍋ご飯は大きめの一枚で締める。全体を「3つの鍋→魚→米」の順でつなぐ。常時スライダーや横スクロールに隠さず、5品を通常の縦スクロールで読めるようにする。

スマートフォンでは5品を1列で表示し、写真→料理名／価格→短い説明の順で統一する。画像の重要な具材や器を切らず、元画像の比率を尊重する。

| 土鍋ご飯 | 2,199円 | 集合写真にご飯らしき器はあるが、該当商品・単品写真は特定できず |

2026-11-02のユーザー回答：「どれがどの画像かは不明」。したがって、上記候補を確定対応として扱わない。エビの揚げ物らしき写真をエビ麻辣鍋に流用したり、鍋やご飯の商品写真を生成して代用したりしない。商品説明は確認済み情報の範囲に留め、具材や味付け、提供人数を勝手に追加しない。

価格の税込／税別、1人前／1皿、鍋の注文条件は未確認。提供表記「通風鍋」はそのまま記録し、一般的な表記「痛風鍋」への変更は正式名称確認後に行う。

### D. 日本酒「今夜の一杯を、選ぶ楽しみ。」

背景を深い藍へ切り替える。`S__49111056_0.jpg` を横に広く置き、写真に一部重なるように短い見出しと「日本酒20種以上」を配置。瓶の銘柄が写っていても、常設・現在提供中とは断定しない。銘柄リストや価格は追加資料がある場合のみ掲載する。

### E. 店内「集まる日も、ふらっと一杯も。」

`S__49111057_0.jpg` の実際の内観を主役にする。写真の下に「40席・全席テーブル・貸切可」を一行で整理し、デート／女子会から宴会／家族利用／接待まで対応できることを短文で伝える。利用シーンごとの同形カードは並べない。

内観素材は現状1枚のため、同じ写真を繰り返して広い店舗に見せたり、別角度の店内を生成したりしない。個室の有無は断定しない。最大50名は条件確認後に追記する。

### F. 料理の余韻とInstagram

補助の料理写真から2〜3枚を選び、横幅と開始位置を変えた短い写真帯をつくる。素材 `S__49111060_0.jpg`、`S__49111061_0.jpg`、`S__49111064_0.jpg`、`S__49111065_0.jpg` が候補。品名・価格は付けず、実際の料理の雰囲気を伝える。Instagramへのリンクは「お店のInstagramを見る」。API連携や埋め込みに依存せず、読み込みを軽くする。

### G. アクセス・店舗情報・フッター

看板実写 `S__49111067_0.jpg` を来店時の目印として掲載する。看板からロゴを切り抜いて流用しない。住所、営業時間、休み、席、決済、電話を見やすい表にまとめる。

「Googleマップで経路を見る」と電話CTAを配置する。マップのピン・入口経路は実装時に確認し、未確認の駅出口名やエレベーター経路を記載しない。駅直結という提供事実から「雨に濡れずに来店できる」等へ説明を広げない。

フッターは生成ロゴ、店名、電話、Instagram、ページ内リンクで簡潔にまとめる。

## 5. 来店・予約のUI

- PC：ヘッダーの「電話で予約・お問い合わせ」を主導線とする。
- スマートフォン：下端に「電話」と「地図」の2ボタンを固定。セーフエリアと本文下余白を確保し、料理名・価格・フッターを隠さない。
- ヒーロー内の中央コピー付近にはボタンを重ねず、視線を整理する。
- アンカー移動時は固定ヘッダー分の位置を補正する。電話ボタンはタップ前に用途と番号が分かる表示にする。

## 6. アニメーション計画（GSAP／Lenis）

既存package.jsonにAstro、GSAP、Lenisの依存指定があることを確認済み。インストール状態・ビルド動作は今回未検証。

| 場所 | 動き | 目安・目的 |
| --- | --- | --- |
| 初期表示 | 背景を1.025倍から等倍、ロゴ→短いコピーの順に薄く表示 | 約0.8〜1.0秒。待機用のローディング画面は設けない |
| 料理・見出し | 下から12〜20px移動＋フェード、一度だけ表示 | 約0.55〜0.75秒。隣り合う要素の差は0.08〜0.12秒 |
| PCの大写真 | スクロールに応じた小さな上下移動 | 画像高の数％以内。主役の器が切れる場合は無効 |
| 日本酒・店内 | セクション到達時に見出しと写真を穏やかに表示 | 同じ演出の過剰な反復を避ける |
| ボタン | 色・矢印の小さな移動 | 0.15〜0.2秒。タッチ端末ではhover前提にしない |
| ヘッダー | ヒーロー通過後に背景色と文字色を切り替える | 内容や高さは大きく変えず、位置のずれを避ける |

Lenisは主にPCのホイール操作で軽く使用し、タッチ操作は自然な縦スクロールを優先する。GSAP tickerとLenisの更新ループを一本化し、ScrollTriggerとスクロール位置を同期させる。二重のrequestAnimationFrameを作らない。

`gsap.matchMedia()`で画面幅と`prefers-reduced-motion`に応じた分岐・破棄を行う。動きを減らす設定ではLenis、パララックス、拡大移動を停止し、内容を最初から表示する。JavaScriptが無効・失敗でも本文と画像とリンクを読める設計にする。

長いスクロール固定、強制的な横移動、カーソル追従、永続的な文字流し、スクロール量に対して過大な遅延は採用しない。

## 7. 素材・画像の扱い

全15枚の一覧は `asset-contact-sheet.jpg`。原本は変更しない。素材の内容・候補用途は `asset-inventory.md` に記録する。

660×370pxの素材が多い。原寸を大幅に超える表示や強い切り抜きは避け、写真の解像感と器全体の見え方を実機で確認する。大きなヒーローは別途生成画像を用い、低解像度の料理実写を全面背景に引き伸ばさない。PCの高密度画面で特に気になるものは高解像度原本を確認対象とする。

ヒーロー画像とロゴは生成素材として由来・プロンプトを記録する。ロゴは透明背景の墨色マスターを作成し、白版はCSSの表示処理などで管理する。生成ロゴの「凪」「居酒屋」の字形・小サイズ可読性を目視確認する。店舗看板と同一の既存ロゴとは表示しない。

実装ではAstroの画像最適化を利用し、用途別サイズ・WebP／AVIF等を検討する。ヒーローは優先読み込み、下部写真は遅延読み込み。寸法を指定してレイアウトの揺れを防ぐ。生成画像を料理のalt、OGPの店舗実写、Restaurantの実写画像として扱わない。

## 8. Astro実装構成案

```text
src/
  assets/
    （既存のクライアント提供写真）
    generated/                # 生成ヒーロー・生成ロゴ
  components/
    SiteHeader.astro
    Hero.astro
    Introduction.astro
    SignatureMenu.astro
    SakeSection.astro
    InteriorSection.astro
    FoodGallery.astro
    AccessSection.astro
    SiteFooter.astro
    MobileActions.astro
    Seo.astro
  data/
    site.ts                   # 店舗情報・連絡先・リンク
    menu.ts                   # 名称・価格・写真候補／確認状況
  layouts/
    BaseLayout.astro
  scripts/
    main.ts                   # GSAP・Lenis・メニュー開閉
  styles/
    global.css
  pages/
    index.astro
```

基本はAstroコンポーネントと通常のCSS・TypeScriptで構成し、このLPのためにReact等は追加しない。コンポーネント固有の装飾はscoped CSS、色・余白・文字・共通UIはglobal.cssに集約する。

SEOは日本語ページ、店舗名・日暮里・魚・米が自然に伝わるtitle／description、適切な見出し、実写のOGPを計画する。正式URL確定後にcanonical・サイトマップ等を設定し、Restaurant構造化データは確認済み事実のみ記述する。架空の評価や不明な価格帯、座標は入れない。SEO実装と検索順位・インデックス登録を同一視しない。

開発サーバーの起動はプロジェクト指示どおり `astro dev --background`。管理は `astro dev status`、`astro dev logs`、`astro dev stop` を使う。

## 9. 実装前後の進め方・完了条件

1. 写真対応と料金条件を確定する。対応が分からない場合は、料理写真のラベルを推測で確定せず、制作上の保留として残す。
2. 生成ヒーロー・ロゴを確認し、PC／モバイルのヒーロー構図を確定する。
3. 本計画を基に静止状態のページを実装し、実写写真と情報の読みやすさを調整する。
4. GSAP／Lenisを加え、操作性・画像切り抜き・動きを減らす設定を確認する。
5. ビルド、320／390／768／1440px前後の表示、電話・地図・Instagramのリンク、横はみ出し、固定CTAの重なり、キーボード操作、JS無効時の閲覧性を検証する。

公開前の確認対象：5品すべての写真対応／税込区分／注文単位／「通風鍋」の正式表記／最大50名の利用条件／Instagram・地図の実リンク。席の説明は確認が終わるまで40席・全席テーブル・貸切可の範囲とする。
